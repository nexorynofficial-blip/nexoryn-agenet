Generated by reading the actual source. All field names, types, and schemas below are quoted or paraphrased directly from code, with file paths and line references so this stays traceable.

## 2. Category branching logic

### 2.1 Service dropdown values

Defined in `admin/src/lib/constants.ts:43` and mirrored in `backend/src/services/validation.ts:76`:

```ts
export const SERVICES = ["Automation", "Web Development", "Brand & Graphic Design"] as const;
```

⚠️ **Naming inconsistency already in the codebase** (flagged in a comment at `backend/prisma/schema.prisma:136-141`): `Project.service` uses the string `"Brand & Graphic Design"`, but `Review.service` and `ServiceCategory.serviceName` elsewhere in the same DB use bare `"Graphic Design"`. There are only ever these **3** values for `Project.service` — do not conflate with the 2-value `"Graphic Design"` variants used by Reviews/Services-page content, and do not invent a 4th category.

### 2.2 Where branching happens

All in `admin/src/pages/ProjectForm.tsx`:
- `const isDesign = service === "Brand & Graphic Design";` (line 121) — the single flag that drives every branch.
- Photo field branch: `service === "Web Development" ? <single Photo + Live preview URL> : <Photos multi-uploader>` (lines 360–399).
- Case-study tab set: `const tabs = isDesign ? DESIGN_TABS : STANDARD_TABS;` (line 125) — i.e. **Automation and Web Development share the same tab set and schema shape** ("standard"); only Brand & Graphic Design gets the different "design" shape. There is no separate branch for Automation vs. Web Development in the case-study editor itself — they differ only in the photo/live-preview handling and in one field inside `caseStudy` (`extraKind`, see §3).
- Tab content rendering: `isDesign ? <DesignCaseStudyEditor .../> : <StandardCaseStudyEditor .../>` (lines 436–440).
- Backend enforces the same pairing: `projectInputSchema`'s `.refine()` in `backend/src/services/validation.ts:308-315` — `caseStudy` must contain `designProcess` if and only if `service === "Brand & Graphic Design"`.

### 2.3 Per-category top-level field differences

| Service | Photo field(s) | Case Study tabs (in order) |
|---|---|---|
| **Automation** | "Photos" — multi-image pool via `MultiImageUploader`, one flagged as thumbnail (`Project.photoId`); every image (including the thumbnail) appears in the gallery. | `STANDARD_TABS`: Overview → Results → Tech Stack → Scalability & Flexibility |
| **Web Development** | Single "Photo" via `AssetPicker` modal, plus a "Live preview URL" text field (blank = "coming soon" on the public site). No gallery pool. | `STANDARD_TABS`: Overview → Results → Tech Stack → Scalability & Flexibility |
| **Brand & Graphic Design** | "Photos" — same multi-image pool/thumbnail mechanism as Automation. | `DESIGN_TABS`: Overview → Design Process → Key Features → Use Cases → Customization & Scalability |

Tab constants, `admin/src/pages/ProjectForm.tsx:27-28`:
```ts
const STANDARD_TABS = ["Overview", "Results", "Tech Stack", "Scalability & Flexibility"];
const DESIGN_TABS = ["Overview", "Design Process", "Key Features", "Use Cases", "Customization & Scalability"];
```
These must match `BASE_TABS`/`DESIGN_TABS` in the public site's `src/pages/CaseStudyPage.jsx` (referenced in a comment at line 22 of ProjectForm.tsx — not re-verified here, but that's the file to check if a public-page tab ever looks out of sync with the admin form).

Note: there is **no separate image-gallery tab** in the Case Study editor for any category — that was consolidated into the single "Photos" section outside the tabs (comment at `ProjectForm.tsx:22-26`), specifically so the thumbnail can never drift out of sync with the gallery.

### 2.4 Switching Service mid-edit

`admin/src/pages/ProjectForm.tsx:149-168` — switching the Service dropdown after already adding images does **not** discard them:
- Web Development → non-Web-Dev: the current single `photo` becomes the first (and thumbnail) entry of `mediaItems`.
- non-Web-Dev → Web Development: the currently-thumbnailed `mediaItems` entry becomes the single `photo`; `mediaItems` is cleared.
- Skipped on initial load of an existing project (`hasLoadedRef`), so hydrating doesn't spuriously trigger this.

## 4. What "Save Project" actually does

**There is no draft/unpublished state.** Clicking "Save Project" creates the row via `POST /api/v1/admin/projects` (or updates via `PUT .../:id`) and it is immediately live — any project row in the `Project` table is served as-is by the public site's read path. There is no `status`, `published`, `visible`, or `draft` column on `Project` at all.

Confirmed by reading `backend/prisma/schema.prisma:131-168` (`model Project`) in full — its only boolean/visibility-adjacent fields are:
```prisma
model Project {
  id    String @id @default(cuid())
  slug  String @unique
  title String
  industry    String
  service     String
  description String
  tags        String[]
  photoId String
  photo   Asset  @relation("ProjectPhoto", fields: [photoId], references: [id], onDelete: Restrict)
  caseStudy Json
  isFeatured    Boolean @default(false)
  featuredOrder Int?
  createdBy String?
  creator   AdminUser? @relation(fields: [createdBy], references: [id], onDelete: SetNull)
  createdAt DateTime   @default(now())
  updatedAt DateTime   @updatedAt

  @@index([industry])
  @@index([service])
  @@index([isFeatured])
}
```
`isFeatured`/`featuredOrder` only control **homepage featuring**, not portfolio visibility — an unfeatured project still shows on the full portfolio list. There is no other status-like field anywhere for this model. (For contrast: `InternalProject.status` — `"active" | "archived" | "completed"` — and `ContactSubmission.status` — `"new" | "read" | "handled"` — exist on unrelated models, and are not applicable here.)

### 4.1 API endpoint

Source: `backend/src/routes/admin/projects.ts` (mounted, per the frontend calls in `ProjectForm.tsx`, under `/api/v1/admin/projects`).

- **Create**: `POST /api/v1/admin/projects`
- **Update**: `PUT /api/v1/admin/projects/:id`
- **List**: `GET /api/v1/admin/projects`
- **Read one**: `GET /api/v1/admin/projects/:id` (looked up by internal `id`, not `slug`)
- **Reorder/feature toggle only**: `PATCH /api/v1/admin/projects/:id/reorder` — body `{ isFeatured?: boolean; featuredOrder?: number | null }` (`reorderSchema`, inline in the route file) — this is the closest thing to a "visibility" control, and it only affects homepage featuring.
- **Delete**: `DELETE /api/v1/admin/projects/:id`

All routes are behind `router.use(authMiddleware)` (see §4.3) — there is no `requireRole` restriction on the projects router, so any authenticated admin account (not just "owner" partners) can create/edit/delete projects.

### 4.2 Request body shape

The full Zod schema actually used server-side to validate `POST`/`PUT` bodies, `backend/src/services/validation.ts:227-317`:

```ts
const bulletList = z.array(z.string().min(1)).default([]);
const workflowStep = z.object({ icon: z.string().min(1), label: z.string().min(1) });
const titledDescription = z.object({ title: z.string().min(1), description: z.string().min(1) });
const galleryShot = z.object({
  src: z.string().min(1),
  alt: z.string().min(1),
  width: z.number().int().positive().optional(),
  height: z.number().int().positive().optional(),
});

const standardCaseStudySchema = z
  .object({
    category: z.string().min(1),
    techIcons: z.array(z.object({ name: z.string().min(1), icon: z.string().min(1) })),
    summary: z.string().min(1),
    overview: z.object({
      problem: bulletList,
      solution: bulletList,
      workflow: z.array(workflowStep),
      breakdown: z.array(titledDescription),
    }),
    results: z.object({
      keyFeatures: z.array(titledDescription),
      before: z.string().min(1),
      after: z.string().min(1),
      proof: z.string().min(1),
    }),
    techStack: z.record(
      z.string(),
      z.array(z.object({ name: z.string().min(1), role: z.string().min(1), icon: z.string().min(1) })),
    ),
    scalability: z.array(titledDescription),
    screenshots: z.array(galleryShot).optional(),
    gallery: z.array(galleryShot).optional(),
    livePreview: z.union([z.string().url(), z.literal(true)]).optional(),
  })
  .refine(
    (cs) => [cs.screenshots, cs.gallery, cs.livePreview].filter((v) => v !== undefined).length <= 1,
    { message: "Only one of screenshots / gallery / livePreview may be set" },
  );

const designCaseStudySchema = z.object({
  category: z.string().min(1),
  techIcons: z.array(z.object({ name: z.string().min(1), icon: z.string().min(1) })),
  summary: z.string().min(1),
  overview: z.object({
    problem: bulletList,
    solution: bulletList,
  }),
  designProcess: z.object({
    input: bulletList,
    workflow: z.array(workflowStep),
    engine: z.string().min(1),
    refinements: z.string().min(1),
    qa: z.string().min(1),
  }),
  keyFeatures: z.array(titledDescription),
  useCases: z.array(titledDescription),
  scalability: z.array(titledDescription),
  gallery: z.array(galleryShot).min(1, "Design case studies require at least one gallery image"),
});

export const projectInputSchema = z
  .object({
    slug: z
      .string()
      .min(1)
      .regex(/^[a-z0-9]+(-[a-z0-9]+)*$/, "Slug must be lowercase, hyphen-separated"),
    title: z.string().min(1).max(200),
    industry: z.string().trim().min(1, "Industry is required").max(100),
    service: z.enum(SERVICES), // SERVICES = ["Automation", "Web Development", "Brand & Graphic Design"]
    description: z.string().min(1).max(1000),
    tags: z.array(z.string().min(1)).default([]),
    photoId: z.string().min(1),
    caseStudy: z.union([standardCaseStudySchema, designCaseStudySchema]),
    isFeatured: z.boolean().default(false),
    featuredOrder: z.number().int().optional(),
  })
  .refine(
    (p) => {
      const isDesign = "designProcess" in p.caseStudy;
      if (p.service === "Brand & Graphic Design") return isDesign;
      return !isDesign;
    },
    { message: "caseStudy shape must match `service` (design shape only for Brand & Graphic Design)" },
  );

export type ProjectInput = z.infer<typeof projectInputSchema>;
```

This `projectInputSchema` (not `req.body` directly) is exactly what the route parses (`projectInputSchema.parse(req.body)` — `backend/src/routes/admin/projects.ts:42` and `:60`) — anything not in this shape is rejected with a 422 by the global Zod error handler (inferred from the `parse()` throwing pattern used elsewhere in this file, e.g. `validateContactForm`'s doc comment: "Throws a ZodError ... on failure").

Note the JSON `payload` the frontend actually constructs (`ProjectForm.tsx:259-270`) matches this schema key-for-key: `{ slug, title, industry, service, description, tags, photoId, caseStudy, isFeatured, featuredOrder }`. `caseStudy` is always one concrete flat object; there's no `standard`/`design` wrapper key sent — that split is an admin-editor-only construct (`toRawCaseStudy()` in `CaseStudyEditor.tsx:140-167`) collapsed into one JSON blob before sending.

### 4.3 Auth mechanism

`backend/src/middleware/auth.ts` (`authMiddleware`, applied to the whole projects router via `router.use(authMiddleware)`):
- Primary: **httpOnly session cookie**, name = `SESSION_COOKIE_NAME` (from `backend/src/utils/jwt.ts`), read via `req.cookies[SESSION_COOKIE_NAME]`.
- Fallback: `Authorization: Bearer <token>` header — same JWT format, explicitly supported "for non-browser API clients."
- The admin's dashboard `fetch` client (`admin/src/lib/api.ts:20-23`) sends `credentials: "include"` and does **not** set an `Authorization` header — it relies entirely on the cookie. So for direct API calls (e.g. from an agent, not a browser), the Bearer fallback is the practical way in: `Authorization: Bearer <admin JWT>`.
- On every request, the admin is **re-read from the DB** (not trusted purely from JWT claims) and checked against `admin.sessionsValidFrom` for revocation.
- No `requireRole()` gate is applied to the projects or assets routers — any valid authenticated admin account can create/edit/delete projects and upload/delete assets (role gating exists elsewhere, e.g. Finance, per the comment in `auth.ts:60-68`, but not here).

### 4.4 Is there a way to create an unpublished / not-yet-visible project via the API?

**No.** There is no `status`/`draft` field anywhere on `Project`, no separate "draft" endpoint, and no request parameter accepted by `projectInputSchema` that would create a hidden project. `POST /api/v1/admin/projects` is the only creation path, and any row it creates is immediately live on the public site the same way `GET`-ing it back would show it (nothing filters `Project` reads by any visibility flag). If you want a "prepared but not yet public" workflow for your agent, that would need a new schema field and public-read filter added — it doesn't exist today.

Practical implication for your agent's design: calling `POST /api/v1/admin/projects` directly (with a valid Bearer token) **is** viable and is the more reliable path vs. browser automation — but be aware it publishes immediately, with no staging step. If that's undesirable, the safest pattern is to build the payload and hold it (e.g. write to a local review file) before calling the endpoint, rather than relying on any server-side draft state, since none exists.

## 5. Photo/image handling

### 5.1 Storage model

- Every uploaded image becomes one row in the `Asset` table (`backend/prisma/schema.prisma:275-293`):
```prisma
model Asset {
  id       String @id @default(cuid())
  url      String
  altText  String
  width    Int?
  height   Int?
  mimeType String
  fileSize Int
  uploadedBy String
  uploader   AdminUser @relation(fields: [uploadedBy], references: [id])
  uploadedAt DateTime  @default(now())
  projectPhotos Project[]    @relation("ProjectPhoto")
  teamPhotos    TeamMember[] @relation("TeamMemberPhoto")
  @@index([uploadedAt])
  @@index([uploadedBy])
}
```
- `url` is a Cloudinary `secure_url` (images are uploaded to Cloudinary, not stored as base64 or on local disk — see `backend/src/services/storage.ts`).
- `Project.photoId` is a real foreign key to one `Asset` row (`onDelete: Restrict` — you cannot delete an Asset that's in use as a project's thumbnail; `assets.ts:102-112` also blocks deleting an Asset in use by any project or team member).
- Gallery images inside `caseStudy` (the `gallery`/`screenshots` arrays) are stored as **plain embedded objects**, not foreign keys: `{ src: string, alt: string, width?: number, height?: number }` (the `galleryShot` Zod shape). `src` is just the Cloudinary URL string, duplicated from whatever Asset it came from — there's no `assetId` reference inside the JSON blob.

### 5.2 Thumbnail selection

- Recorded as `Project.photoId` (a single scalar FK column) — not a flag on an array element, not derived from array order.
- In the admin form, for Automation/Brand & Graphic Design, the thumbnail is whichever `Asset.id` matches `thumbnailId` in `MultiImageUploader`'s local state (a star toggle per row, `admin/src/components/MultiImageUploader.tsx:104-113`); the first image added defaults to being the thumbnail (line 56-60). On submit, `photoId = thumbnailId` (`ProjectForm.tsx:243`).
- For Web Development, there's no separate "pick a thumbnail" step — the single `Photo` chosen *is* both the thumbnail and (via `caseStudy.livePreview`) the only image, since Web Development projects don't have a gallery at all.
- **Design detail worth knowing**: for Automation/Design projects, the thumbnail image is *also* always one of the entries in the case-study gallery (`ProjectForm.tsx` comment at lines 1-8 of `MultiImageUploader.tsx`: "There is deliberately no separate 'Photo' field and 'Gallery' tab ... one list, one place to manage it, so the thumbnail is never accidentally left out of the gallery or vice versa"). If your agent constructs a payload by hand, make sure the thumbnail's `{src, alt, ...}` is included in the `gallery` array it sends, matching `photoId`'s Asset URL.

### 5.3 Upload API

Yes — a direct multipart upload endpoint exists and does not require the browser file picker:

`POST /api/v1/admin/assets` (`backend/src/routes/admin/assets.ts:65-92`)
- Content-Type: `multipart/form-data`
- Fields: `file` (binary, required) + `altText` (string, required, trimmed non-empty)
- Server validates: MIME type must be one of `["image/jpeg", "image/png", "image/webp", "image/gif"]` (`isValidImageMime`, `storage.ts:24-28`); max size 10MB (`multer` limit, `assets.ts:21`, explicitly re-validated server-side "never trust the admin form's `<input accept>` alone").
- On success (`201`): returns the created `Asset` row (`{ id, url, altText, width, height, mimeType, fileSize, uploadedAt, uploader }`), where `url`/`width`/`height` come straight from Cloudinary's response.
- Also present: `GET /api/v1/admin/assets` (paginated list, cursor-based via `?after=<assetId>`, page size 20), `POST /api/v1/admin/assets/lookup-by-url` (bulk-resolve gallery `src` URLs back to `Asset` rows — body `{ urls: string[] }`, max 100), `DELETE /api/v1/admin/assets/:id` (blocked with 409 if the asset is still referenced by any `Project.photoId` or `TeamMember.photoId`).
- Same `authMiddleware` auth as the projects routes (cookie or Bearer).

For your agent: upload each image via `POST /api/v1/admin/assets` first to get back a real `Asset.id` + `url`, then reference that `url` (and, for the thumbnail, that `id` as `photoId`) when building the `POST /api/v1/admin/projects` payload.

## 6. Slug generation

- **Client-side convenience only**, not authoritative: `admin/src/pages/ProjectForm.tsx:30-36`
```ts
function slugify(input: string): string {
  return input
    .toLowerCase()
    .trim()
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "");
}
```
  Auto-applied to a **new** project's slug field as the title is typed, until the admin edits the slug field directly (`slugManuallyEdited` state, `ProjectForm.tsx:103-104, 138-140`) — at which point it's treated as deliberately chosen and left alone. Never re-runs automatically for an **existing** project (its slug is already a live URL).
- **Format validation, server-side**: `projectInputSchema.slug` requires `/^[a-z0-9]+(-[a-z0-9]+)*$/` — lowercase alphanumerics separated by single hyphens, no leading/trailing/double hyphens.
- **Uniqueness**: enforced only server-side, in `backend/src/routes/admin/projects.ts`:
  - Create (`POST`, lines 44-45): `prisma.project.findUnique({ where: { slug: input.slug } })` — if found, throws `ApiError.conflict("A project with this slug already exists", { slug: "Already in use" })`, which surfaces as **HTTP 409**.
  - Update (`PUT`, lines 65-68): same check, but only runs if the slug actually changed (`input.slug !== existing.slug`), so keeping an existing project's own slug never self-conflicts.
  - `Project.slug` also has a DB-level `@unique` constraint (`schema.prisma:133`), so this is a hard guarantee, not just an app-layer check.
- **On collision**: the request is rejected outright (409, with `fields: { slug: "Already in use" }`); nothing is auto-suffixed or renamed. Your agent should catch a 409 on `slug` and either ask for a different title/slug or append a disambiguator (e.g. `-2`) and retry — there's no server-side dedup helper to call instead.

## 7. Form implementation details

### 7.1 Form library

**None** — plain React `useState` per field (no React Hook Form, no Formik). Validation is manual (`if (!industry.trim()) setError(...)` etc. in `handleSubmit`, `ProjectForm.tsx:214-289`) plus whatever the backend's Zod schema rejects after the fact (surfaced via `ApiRequestError.fields`).

### 7.2 Single shared type/schema

There are **two** separate definitions of the "Project" shape that must be kept in sync by hand (no shared package/import between the admin app and backend):

1. **Frontend TS interface** — what the admin app expects a fetched project to look like (`admin/src/types/index.ts:13-28`):
```ts
export interface Project {
  id: string;
  slug: string;
  title: string;
  industry: string;
  service: "Automation" | "Web Development" | "Brand & Graphic Design";
  description: string;
  tags: string[];
  photoId: string;
  photo: Asset;
  caseStudy: Record<string, unknown>;
  isFeatured: boolean;
  featuredOrder: number | null;
  createdAt: string;
  updatedAt: string;
}
```
   (`Asset` interface is right above it, quoted in §5.1-adjacent form in `types/index.ts:1-11`.)

2. **Backend Zod schema** — the actual runtime-enforced request-body contract, `projectInputSchema` in `backend/src/services/validation.ts`, quoted in full in §4.2. **This is the authoritative shape for anything your agent POSTs/PUTs** — treat §4.2's code block as the source of truth over the TS interface, since the interface only describes *read* shape (it includes server-generated fields like `id`/`createdAt`/full `photo` object that a create request must NOT send, and it doesn't encode any of the validation rules).

There is no single schema describing both directions (read + write) — the two differ in exactly the fields you'd expect (write sends `photoId` only + a flat `caseStudy`; read returns the resolved `photo` Asset object + timestamps + `id`).

### 7.3 Stable id/name/data-testid attributes

None found. Inputs are plain `<Input>`/`<Textarea>`/`<Select>` wrapper components (`admin/src/components/ui`) driven purely by React state/`value`/`onChange` — no `name`, `id`, or `data-testid` props are passed anywhere in `ProjectForm.tsx` or `CaseStudyEditor.tsx`. Field identity in the DOM is therefore **not stable/queryable** by attribute; anything automating this via the browser (rather than the API) would need to locate fields by label text/position, which is fragile across UI edits. This is one more reason the direct-API approach in §4.4 is the more robust integration path for your agent.
